# 调研：抖音 / 小红书按 hubPlatform 接入的可行性

> 日期：2026-10-28　|　对应：开发方案「新增 · B 站视频 · 抖音/小红书接入」　|　结论：**暂不开发**
> 说明：本调研基于对两个平台公开能力的已有了解与 B 站接入（`internal/bilibili`）的实现经验，未在本机实际抓取验证；涉及的平台策略可能随时变化，正式立项前需重新验证。

## 1. 接入需要什么

`cmd/api/hub.go` 的 `hubPlatform` 接口要求平台提供三类能力：

| 能力 | B 站现状 | 抖音 | 小红书 |
|---|---|---|---|
| 频道（账号）解析：主页链接 → 账号 id、名称 | 公开接口 + WBI 签名 | 无开放接口；网页接口需要动态签名参数与登录态 Cookie | 无开放接口；网页接口需要签名参数与登录态 |
| 账号视频列表（分页、按时间） | 公开接口 | 同上，且频繁触发风控验证 | 同上，笔记以图文为主，视频占比小 |
| 字幕 / 文本（AI 摘要的输入） | 人工 / AI 字幕接口 | 大部分视频无字幕文件，需自行语音转写 | 视频无字幕；图文笔记正文可用 |

## 2. 主要障碍

1. **无官方数据 API**：两个平台的开放平台面向「本账号内容管理 / 企业营销」，不提供「读取任意账号公开作品列表」的能力。
2. **反爬与签名**：网页接口请求需要前端 JS 动态生成的签名参数，算法经常变更；B 站接入已经在 WBI 签名、风控报错上投入不少维护成本，抖音/小红书维护成本会明显更高。
3. **登录态与封号风险**：稳定抓取通常需要真实账号 Cookie，高频请求可能导致账号受限。
4. **合规**：两个平台用户协议均禁止未经授权的自动化抓取；本项目是个人站点，但服务器在公网，风险需要负责人确认。
5. **AI 摘要输入缺失**：没有字幕时需额外引入语音转写（如 Whisper），成本和处理时长都显著增加。

## 3. 可行的替代方案（按投入从小到大）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 手动单条收藏 | 在现有页面增加「粘贴分享链接」，只保存链接、标题（手填或从分享文本中解析）、标签与备注，不抓取 | 零风控、零维护 | 无自动更新、无 AI 摘要 |
| B. 单条解析 | 对用户粘贴的单条链接用 yt-dlp 尝试解析（yt-dlp 有抖音提取器，但经常需要 Cookie 且易失效），失败降级为方案 A | 能拿到标题、封面、时长 | 不稳定，需要持续跟进 yt-dlp 版本 |
| C. 自建 RSSHub | 部署 RSSHub 并配置 Cookie，订阅账号路由，再按 hubPlatform 接入 RSS | 复用社区维护的签名逻辑 | 额外服务与 Cookie 维护，路由经常失效 |
| D. 完整 hubPlatform 接入 | 自行实现签名、分页、风控处理与语音转写 | 体验与油管/B 站一致 | 投入最大、维护成本最高、合规风险最高 |

## 4. 建议

- 本期不做完整接入（方案 D）。
- 若确有需求，先做 **方案 A**（约 1 天，前后端各一个表单 + 一张表），观察实际使用频率后再评估方案 B / C。
- 立项前需负责人确认：是否接受账号 Cookie 存放在服务器、是否接受平台协议风险。
